## Context

See proposal.md - Why. Two independent facts combine to produce the escape: (1) `permission-gate.ts`'s bash confinement is purely pattern-based — it inspects the command *string* for path-shaped tokens and has no way to know that an ordinary, unobfuscated CLI invocation (`openspec change new ...`, no path argument at all) resolves a project root by walking up from `cwd`; and (2) `INTROSPECT_WORKSPACE_DIR` defaults to `introspect-harness-server/data/workspace`, nested inside this repo, so that walk finds this repo's real `openspec/` a few levels up. Fixing (1) in general would mean actually parsing/executing commands instead of pattern-matching them — out of scope here (see Risks). This design instead removes the reachable escape target: (2) directly, plus a second, independent barrier that holds even if (2) regresses.

`INTROSPECT_TMP_DIR` already exists (`introspect-harness-server/src/env.ts`) and defaults under the OS temp dir; the `add-introspect-temp-dir-access` design doc deliberately frames that as scratch space it's fine to lose on reboot. The workspace directory is not that: `session-store.ts` seeds it from `templates/agent-workspace/` via `ensureAgentWorkspace`, resets it to that seed between sessions, and `workspace-manager.ts` snapshots/restores it for recording and replay. It also doubles as the pi SDK's session-log key: `SessionManager.create(cwd)` persists chat history under `~/.pi/agent/sessions/<encoded-cwd>/`, so the workspace path is load-bearing for where session logs land, not just where files live.

## Goals / Non-Goals

**Goals:**
- No ancestor directory above the default workspace root contains a project marker (`openspec/`, `.git`, etc.) that an upward-walking CLI tool invoked via `bash` could resolve to.
- The seeded workspace is self-contained for `openspec` specifically: it already qualifies as an OpenSpec root on its own, so even a non-default workspace location (an operator-supplied `INTROSPECT_WORKSPACE_DIR` override) is covered without relying on where that override happens to point.
- The new default location survives process restarts and reboots on the NUC (PM2 always-on) deployment.

**Non-Goals:**
- Not attempting to catch every upward-walking CLI in general (e.g. `git`, `npm`) with a matching pre-seeded marker — only `openspec` is addressed directly, since it's the one observed and the one with obvious legitimate in-sandbox use (the agent's own OpenSpec skills). Goal 1 (physical isolation) is what generalizes to other tools; Goal 2 is `openspec`-specific defense-in-depth on top of it.
- Not changing `INTROSPECT_TMP_DIR`, `RECORDINGS_DIR`, or any other harness-server's workspace layout. `RECORDINGS_DIR` stores server-side snapshots the agent's tools never see as `cwd`, so it isn't part of this escape surface.
- Not replacing the pattern-based bash confinement with real subprocess sandboxing (kernel-level isolation, containers). Still flagged as follow-up, per the original `sandbox-introspect-harness` design's Risks section.
- No automated migration or deletion of the old in-repo `data/workspace` directory.

## Decisions

**New default: `join(homedir(), '.local', 'share', 'introspect-harness', 'workspace')`, override via `INTROSPECT_WORKSPACE_DIR` unchanged.** `env.ts` already imports `node:os` for `tmpdir()`; adding `homedir()` needs no new dependency. This mirrors the existing override pattern exactly — only the default value changes — so `session-store.ts`'s `ensureAgentWorkspace(env.INTROSPECT_WORKSPACE_DIR, TEMPLATES_DIR)` call is untouched.
  - Alternative considered: a project-adjacent-but-sibling path, e.g. `../introspect-harness-workspace` next to the `harness` repo checkout. Rejected — still filesystem-adjacent to the repo in a way that depends on the checkout's parent directory being clean of project markers, which isn't guaranteed (e.g. a `~/work/` directory holding multiple repos might itself gain a stray `openspec/` or `.git` someday). A home-rooted data directory has no such dependency.
  - Alternative considered: pull in `env-paths` (or similar) for proper per-OS XDG/Library conventions. Rejected as unnecessary weight for a single-path decision on a project that already hand-rolls its one other data-dir default (`INTROSPECT_TMP_DIR`) with `node:os` directly — same approach, just `homedir()` instead of `tmpdir()`.

**Pre-initialize `openspec/` in `templates/agent-workspace/` via `openspec init --tools none --no-animation`.** Verified output is `openspec/{config.yaml, specs/, changes/archive/}`. `--tools none` skips writing any AI-tool instruction files, which would otherwise sit alongside the harness's own templated `AGENTS.md` and could confuse the agent about which instructions govern the session. Confirmed against `@fission-ai/openspec`'s actual root-resolution code (`core/root-selection.js`, `core/planning-home.js`, `core/project-config.js`): `findRepoPlanningRootSync` checks `<startPath>/openspec` *before* ever considering a parent, and `classifyOpenSpecDir` only requires `openspec/specs` or `openspec/changes` to exist (`project.md`/`config.yaml` content is not required for `hasPlanningShape`) — so the seeded template alone is sufficient; no `project.md` needs to be authored by hand.
  - Alternative considered: block the `openspec` binary outright in `checkLinkCreation`-style bash confinement (name-token match, same shape as the existing `ln`/`cp -s` ban). Rejected as the sole fix — it only defeats this one CLI; any other tool with the same "resolve project root by walking up, no path argument" shape (a future `git init`, an `npm init -w`, a linter's config-file discovery) would still succeed via the same regex-invisible mechanism. Kept off the table entirely here (not even as a supplement) since the two decisions above already close this specific tool's escape path without narrowing what the agent can legitimately do with it.
  - Alternative considered: block `openspec` from resolving above the workspace by setting an env var it might honor (e.g. a project-root override) on the `bash` tool's environment. Rejected — checked `@fission-ai/openspec`'s CLI options and found no such override besides `--store`/`--store-path` (both explicit CLI flags the agent would have to pass deliberately, not an ambient env var), so there's nothing to set.

## Risks / Trade-offs

- **[Risk]** This is still pattern-based/config-based confinement, not a kernel-level sandbox — the same residual class of bypass (string-built commands, env-var expansion, other non-shell interpreters) that `sandbox-introspect-harness`'s design already flagged remains, unchanged by this fix.
  → **Mitigation**: unchanged from the original design — documented as a known limitation, real subprocess sandboxing stays explicit follow-up work.
- **[Risk]** The pre-seeded `openspec/` directory's effectiveness depends on `@fission-ai/openspec`'s current root-resolution behavior (verified against `1.9.0`), which the harness doesn't pin or vendor — a future version could change what qualifies as a root (e.g. start requiring `project.md` content, or stop treating `specs`/`changes` alone as sufficient) and silently reopen the gap this decision closes.
  → **Mitigation**: this is defense-in-depth layered on top of the primary fix (physical isolation from any ancestor project root), not the only barrier — even if `openspec`'s algorithm changes, there's no ancestor `openspec/`/`.git` left for it to walk up into and find. Worth a periodic sanity check (e.g. as part of upgrading the globally-installed `openspec` CLI) rather than an automated one, given how infrequently that dependency changes.
- **[Trade-off]** Moving the workspace default changes `cwd`, which changes the pi SDK's session-log bucket (`~/.pi/agent/sessions/<encoded-cwd>/`) for anyone running with the default config — existing on-disk session logs under the old encoded path become inactive (not deleted, just no longer written to) once this ships.
  → **Mitigation**: this is inherent to a default-path change and no different in kind from what already happens if an operator overrides `INTROSPECT_WORKSPACE_DIR` today; old logs remain on disk for audit if ever needed, and the single-user/single-process model (per CLAUDE.md) means there's no multi-user history to reconcile.
- **[Trade-off]** The old in-repo `introspect-harness-server/data/workspace/` becomes orphaned (still present, no longer read or written by the server after this ships).
  → **Mitigation**: left alone rather than auto-deleted (destructive, and it's gitignored/local-only anyway); note it in the workspace/dev docs update as safe to remove by hand.

## Migration Plan

No data migration. This is a single always-on process (per CLAUDE.md); the next server restart after this change ships picks up the new default, `ensureAgentWorkspace` seeds the new location fresh from the updated template (now including `openspec/`), and the old `data/workspace` directory is simply no longer touched. Rollback is reverting the two changed files (`env.ts`, `templates/agent-workspace/`) — no state depends on the new location existing.

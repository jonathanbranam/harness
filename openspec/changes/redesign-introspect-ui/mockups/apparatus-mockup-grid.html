Apparatus — redesign mockup (grid)

Rendering approach: a fixed waffle-style grid representing the full 0–100% context window, filling top-left → bottom-right one row at a time (like a contribution heatmap). Because most individual turns are far smaller than one grid cell, nearby chronological entries are aggregated (debounced) until their combined size fills a cell — each cell shows its dominant category, with a secondary-color split when it's a genuine mix. Methodology & findings from grounding this in real data

Source: a real 7-prompt / 58-turn OpenSpec workflow session (create → continue → fast-forward → apply → sync/archive a change), recorded by this harness. Ends at 46,606 / 262,144 tokens (17.8%), comfortably inside the smart zone the whole time.

Thinking is real and substantial: usage.reasoning was 0 on every single message in this session, but 18,853 characters of actual thinking_delta text came through — confirming design.md's finding that thinking-pill presence must key off the delta stream, not the usage field.

New finding, not yet in design.md: a large share of each turn's "new" input tokens (the otherInput/input category here) is not fresh content — it's prior conversation being reprocessed because prompt-cache reuse resets at agent-run boundaries (visible as input spikes right after each agent_start). Worth a Decision note if this pattern holds up outside this one recording.

Skill auto-loads are a distinct, sizeable category: 4 of this session's 7 "user" messages were actually skill files auto-injected into context (<skill name="…"> blocks, 480–590 tokens each after scaling) rather than anything the user typed — split out here as its own pill color since it's exactly the kind of invisible context growth Apparatus exists to surface.

Grid rendering approach: the whole grid is a fixed 24 × 50 = 1,200 cells representing 0–100% of the context window (each cell ≈ 218 tokens here). Chronological entries are walked in order and binned into whichever cell(s) their token range falls in — several small thinking/output/tool-result slivers naturally land in the same cell and show up as one aggregated, hoverable mark (a split-color fill when no single category dominates), instead of each getting its own invisible sliver. Tool calls are still drawn as small dot markers rather than competing for a cell's dominant color, since they're both tiny and worth always being visible regardless of binning.
